1. System Purpose & Architectural Philosophy
The live trading bot ecosystem operates on high-velocity real-time execution (MPT_RPN_WALLET_ADDRESS and the live AMM mesh). Lodestone is a strictly decoupled forensic microservice designed to pierce through high-volume AMM swap noise and trace meme coin origins back to their true deployers and funding sources.
 * Primary Objective: Map multi-account deployment lineages, identify issuer "ghost" funding wallets, and calculate creator confidence scores without creating I/O contention on the live trading engine.
 * The Isolation Rule: Lodestone never shares write paths or execution loops with active trading strategies (Mean Reversion, Four-Hop Atomic, etc.). It utilizes isolated database tables and public full-history RPC fallbacks.
 * Write Once, Cache Forever: Because token deployment histories are immutable, Lodestone walks the historical ledger once per token, commits the resolved relationship tree to QuestDB, and serves subsequent UI queries instantly from cache.

A. The Summary Table: token_lineage
Stores the final resolved origin story of each whitelisted asset for instant GUI retrieval.
CREATE TABLE token_lineage (
    discovered_at TIMESTAMP,
    currency SYMBOL CAPACITY 256 CACHE,
    issuer SYMBOL CAPACITY 100 CACHE,
    funding_wallet SYMBOL CAPACITY 100 CACHE,
    amm_account SYMBOL CAPACITY 100 CACHE,
    amm_create_ledger LONG,
    creator_confidence DOUBLE,
    lineage_status SYMBOL CAPACITY 16 CACHE,
    notes STRING
) TIMESTAMP(discovered_at) PARTITION BY DAY WAL;

B. The Step-by-Step Table: forensic_audit_events
Logs the granular chronological milestone events discovered during historical ledger walks.
CREATE TABLE forensic_audit_events (
    timestamp TIMESTAMP,
    currency SYMBOL CAPACITY 256 CACHE,
    issuer SYMBOL CAPACITY 100 CACHE,
    tx_hash SYMBOL CAPACITY 64 CACHE,
    tx_type SYMBOL CAPACITY 32 CACHE, -- e.g., 'AMMCreate', 'TrustSet', 'Payment', 'AccountSet'
    actor_address SYMBOL CAPACITY 100 CACHE,
    ledger_index LONG,
    payload_json STRING
) TIMESTAMP(timestamp) PARTITION BY MONTH WAL;

3. Forensic Engine & Ledger Walker Specification
Because local rippled nodes maintain a restricted operational window (e.g., ~2,000 to 4,000 recent ledgers), Lodestone's backend engine incorporates specialized crawling logic:
 * Remote Full-History Fallback: Automatically routes historical requests (account_tx, ledger) to robust public full-history archive nodes when querying past genesis blocks.
 * Pagination & Continuation: Implements recursive loop handling utilizing XRPL marker fields to page completely through an account's transactional history back to its inception.
 * Target Transaction Filters: Explicitly ignores routine swap and liquidity churn, filtering raw ledger streams specifically for structural transaction classes:
   * AMMCreate: Establishes initial pool liquidity and day-zero liquidity providers.
   * TrustSet: Maps early token distribution networks and initial holder interactions.
   * Payment (Genesis): Identifies initial reserve funding transfers covering account creation costs.
   * AccountSet: Captures issuer configuration adjustments (transfer fees, flags like DefaultRipple).
 * Metadata Parsing: Inspects transaction metadata (AffectedNodes), specifically parsing CreatedNode entries for new ledger objects and PreviousFields for reserve adjustments.
4. Multi-Account Topology Mapping
Lodestone correlates three distinct layers of account architecture to expose hidden deployers:
 * The Issuer Account: The designated minting address holding custom currency definitions.
 * The Funding "Ghost" Wallet: The external origin account that initially supplied XRP reserves to the issuer. Cross-referencing ghost wallets across multiple tokens exposes repeat creators.
 * The AMM Pool Account: The pseudo-account derived by the ledger for liquidity routing, linked directly to its day-zero creators.

7. Phase G1 — Ghost Wallet Forensic Walk (as built Oct 14, 2026)
Complements the per-token walk with a per-ghost dossier walk: ONE genesis-funding GHOST account under the lens, complete account_tx history (forward, marker-driven, archive fallback — same §3 transport), capturing the wallet-behavior evidence the issuer lens cannot see. Venue attribution over this evidence is Phase G2; derivation is from ledger evidence only (DestinationTag/memo reuse + exact-amount round-trips), never hardcoded exchange address lists.
 * Schema — two new tables, byte-parity across Lodestone/lodestone_init.sql + questdb/init/04-lodestone-lineage-schema.sql, same isolation rule (Lodestone-owned; never written by live engines):
   * ghost_walks — summary versioning row per walk (readers collapse: LATEST ON walked_at PARTITION BY ghost_wallet): status, coverage span (first/last ledger), page/tx census, payment direction counts, tagged-payment & memo counts, distinct counterparty/tag counts, XRP in/out drop sums (delivered_amount truth), linked token tags.
   * ghost_events — evidence row per captured tx: ghost_wallet, tx_hash, tx_type ('Payment'|'TrustSet' blueprint-exact), ghost-relative direction (IN|OUT|SELF|OTHER), counterparty, destination_tag, ledger_index, payload_json (class ghost_payment|ghost_trustline: amounts + delivered truth, Flags incl. tfPartialPayment, hex-decoded Memos[], SourceTag).
 * Engine — walker/ghost.py walk_ghost() streams evidence in bounded ILP batches (budget-capped venue/bot ghosts can carry 10^5+ payments); walker/ghostfilter.py is the account-centric ghost lens (every Payment the ghost sent/received in XRP or any IOU, every TrustSet it signed; swaps/liquidity noise counts only in statistics). Events dedupe on tx_hash against the preloaded row set AND ILP key-merge (re-walks/retries never duplicate). Status semantics mirror §1: COMPLETE (marker exhausted) | PARTIAL (budget tripped — resumable with --force) | NO_ACCOUNT | SKIPPED (cached) | ERROR. Memos are hex-decoded from XRPL wire form for venue fingerprinting.
 * Ops — python3 -m walker --ghost rAddr [--dry-run | --force | --max-pages N]; ghost mode returns the honest exit code of the walk (0 recorded | 1 usage/input | 2 runtime error, including ERROR results). G3 batch: python3 -m walker --ghosts --max-pages N sweeps every topology_nodes GHOST wallet lacking a COMPLETE dossier sequentially (same exit-code lattice, batch-fail-loud like --all; PARTIAL dossiers are resumable by re-running with a bigger budget — evidence dedupe is tx_hash-exact). QuestDB reader grammar: SELECT * FROM ghost_walks LATEST ON walked_at PARTITION BY ghost_wallet;
8. Phase G2 — Ghost Venue Crossref (as built Oct 14, 2026)
Correlates the §7 ghost dossiers across ALL walked ghosts into per-ghost venue attributions and same-exit clusters. Derivation is from ledger evidence ONLY (§7 ruling) — never hardcoded exchange address lists. Engine: topology/ghost_crossref.py (pure correlators + crossref_ghosts() orchestrator mirroring the §4 mapper's load → correlate → skip-unchanged → ILP commit → WAL-drain verify shape). Three signal classes:
 * Tag fingerprints — OUT Payments carrying DestinationTag to one counterparty are the venue deposit pattern (per-user deposit IDs); cross-ghost reuse of the SAME tag value at the SAME counterparty is the strong same-exit signal (delivered_amount truth, never the Amount envelope).
 * Memo fingerprints — repeated hex-decoded MemoType/MemoData identities (the G1 lens decodes XRPL wire form) shared across ghosts at one counterparty.
 * Exact-amount round-trips — ghost A OUT exactly N to relay X and ghost B (A != B enforced) IN exactly N from X within ghost_roundtrip_window_ledgers (default 1440 ≈ 96 min): XRP paired on delivered drop integers, IOUs on identical currency+issuer+value serialization; single-ghost loops stay notes-only noise, never venue evidence; BOTH legs' owners get relay-usage credit (cash-out and cash-in are both venue behavior).
 * Evidence rubric (deterministic, documented, clamp 0.98 — absolute ledger proof stays reserved): 0.30 base (any evidence) + 0.05 per extra tagged event (cap +0.20) + 0.15 cross-ghost tag reuse + 0.10 cross-ghost memo identity + 0.05 per round-trip leg (cap +0.10) + 0.05 same-exit cluster (>= 2 ghosts). venue_label is ledger-derived (cross-ghost tag fingerprint | own deposit tag | memo identity | relay) — never a hardcoded venue name.
 * Schema — one new table, byte-parity across both SQL files, same isolation rule: ghost_venues (designated attributed_at; readers collapse with SELECT * FROM ghost_venues LATEST ON attributed_at PARTITION BY ghost_wallet, venue_address;) — venue_label, evidence_score, tagged/memo/roundtrip census, distinct tags, bounded memo_fingerprints, crossref_ghosts (same-exit members) and a notes census (the skip-compare key). Constellation-edge emission into topology_edges was deferred as optional G2.1 — RESOLVED in Phase G3 via the account-scoped convention (VENUE nodes + VENUE_LINK edges with currency/issuer=''; §13).
 * Ops — python3 -m topology --ghosts [--ghost rAddr] [--dry-run | --force]; exit codes 0 attributed | 1 usage/empty | 2 runtime error (parity with §4/§7 CLIs). Re-runs are idempotent: attributions whose notes census is unchanged are skipped; --force re-attributes. Per-ghost event reads are bounded by ghost_crossref_event_cap (LODESTONE_GHOST_CROSSREF_EVENT_CAP, default 100,000 rows; window override LODESTONE_GHOST_ROUNDTRIP_WINDOW_LEDGERS). Every run also emits the G3 constellation pair for each attributed (ghost, venue) — one VENUE node + one VENUE_LINK edge (§13), skip-compared on the census payload; memo fingerprints/labels normalize control characters to spaces exactly like the ILP storage sanitizer (byte-stable re-runs).
